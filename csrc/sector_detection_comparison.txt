Here's some information on how many sectors in total as well as good sectors
the Python version detects for a few common test tracks, as well as a comment
showing the best grid-search result so far. Note the relatively strong
performance of corrupted sector detection, which is basically an approximate
string search on the MFM train representation of the A1A1A1F* preamble sequence.

Also note that even without dewarping, the Python implementation finds a
good sector for 77-4-t78. The "brute-forced band" strategy, which tries to
fit three frequency bands for 01, 001, and 0001, so that there are no MFM
errors upon decoding and so that the AM decodes properly, really does work
well.

No once-through decoder I've tested can find even a single good sector for
t78; I think the problem lies in its once-through nature, as the extreme
noise in one sector can throw off the mean for the next sector.

In comparison, the best grid search result with once-through strategy
(where the whole flux record is decoded at once) is one-mode DP with
			Number of sectors: 20	Bood sectors: 17,
and this seems to be a fluke. More reliable results give 16/20.
So we can meet brute-forcing, but not surpass it. However, the once-
through decoders are quite good at finding start-of-sector metadata;
even though we only get 16 good sectors, they find 20 in total, which
is more than brute-force without dewarping does.

a rather large number of sector-start metadata parts. But every pulse
decoder has trouble getting good sectors. Perhaps we need corrupt preamble
detection (i.e. no longer doing everything "once-through").

Once-through fails completely: none of the pulse decoders manage to
get even a single good sector. I suspect the problem lies in some
sectors being so corrupted that they drag the clock away from any
reasonable estimate, and that the decoders then have no way to get back
to a good estimate for the next sector.
